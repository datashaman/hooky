# Workflows

A running list of the automations that trigger Hooky, or that Hooky itself runs on a schedule/event. Each entry names the trigger, what it does, and where it lives. Add new entries here as they're introduced.

## 1. Hooky GitHub Actions loop

- **File**: [`.github/workflows/hooky.yml`](../.github/workflows/hooky.yml)
- **Triggers and modes**: how deliberate the trigger is decides what runs, not whether the target is an issue or a PR:
  - `workflow_dispatch`, or `issues` labeled `hooky:run`, or a `/hooky run`/`/hooky go` comment on an issue → **implement**: the full planner → contract negotiation → generator/evaluator attempt loop.
  - `pull_request` labeled `hooky:run`, or a `/hooky review` comment on a PR → **review**: a read-only pass (no contract, no writes) that posts a `gh pr review` instead of a branch/PR.
  - `/hooky <text>` comment on a PR (anything but `review`) → **light-implement**: the comment is already a scoped, specific ask, so it skips the planner and contract negotiation and goes straight to a generator/evaluator attempt against it.
  - Any other `/hooky <text>` comment on an issue → **refine**: no run, no model call at all. GitHub already persisted the comment; it's just context for a future run (see below).
- **Identity**: each trigger derives a `run_key` (`issue-<n>`, `pr-<n>`, or `manual-<run_id>`) from the event payload. All durable state, the eventual branch (`hooky/<run_key>`), and the PR title key off this — not the CI `run_id`, so reruns on the same issue/PR resume the same branch/PR instead of spawning new ones.
- **Refining an issue before it runs**: a freeform `/hooky <text>` comment on an issue does nothing by itself — it's meant to sharpen the ask before the full loop actually runs. Whenever `implement` mode does run against an issue (via the label or `/hooky run`/`/hooky go`), the workflow fetches the issue's full comment thread and folds every `/hooky`-prefixed comment's text into the proposal, so refinements made across several comments all reach the loop at once. Hooky's own status comments never start with `/hooky`, so they can't feed back into a future proposal as bloat.
- **What it does**: checks out the repo (pinned to the PR's merge ref for `issue_comment`-on-a-PR events, since that event's default checkout ref is otherwise the default branch, not the PR's code), derives the mode/run_key/proposal, and runs `hooky run`, `hooky run --light`, or `hooky review` accordingly. `implement`/`light-implement` package the resulting working-tree diff (excluding `.hooky/`) into a commit on `hooky/<run_key>`, open or reuse a PR (with a `Relates to #<n>` backlink to whatever triggered the run), and comment the result back on the originating issue/PR. `review` posts a `gh pr review` instead. `refine` posts a one-line acknowledgment and does nothing else. `.hooky/runs/<run_key>/` is uploaded as a workflow artifact for every mode except `refine`.
- **Failure modes**: retriggering the same issue/PR doesn't resume prior loop state — each run is a fresh checkout, so contract negotiation restarts and the final push force-overwrites `hooky/<run_key>`. If `gh pr create`/`gh pr list` fails after a passing loop, the issue/PR comment says so explicitly and points at the pushed branch rather than reporting a bare "passed" with no way to find the work.
- **See also**: [`docs/usage-sequences.md`](usage-sequences.md) for the full sequence diagram ("GitHub Event Flow").

## 2. Locally forwarded GitHub events

- **File**: [`src/hooky/cli/commands/listen.py`](../src/hooky/cli/commands/listen.py) (`hooky listen`), sharing its event-derivation logic with `hooky.yml` via [`src/hooky/shared/github_event.py`](../src/hooky/shared/github_event.py) — `hooky.yml` now imports that module directly (via `uv run`) rather than keeping a separate inline copy, so the two trigger surfaces can't drift.
- **Trigger**: `gh webhook forward` (or an equivalent GitHub webhook relay) streams repo events — issues, PRs, comments, labels — to `hooky listen`'s local HTTP endpoint instead of (or alongside) GitHub Actions. GitHub itself never contacts your machine directly: `gh webhook forward` opens an outbound connection from your machine to a GitHub-hosted relay and forwards deliveries down that connection, so no inbound port needs to be reachable from the internet.
- **Trigger conditions and mode/run_key/proposal derivation match workflow #1** (`determine_mode`/`derive_run_from_event` in `shared/github_event.py`), except comment-thread folding for `implement` mode on issues, which only `hooky.yml` does (it needs `gh api`, which assumes a GitHub remote). Locally, `hooky listen` dispatches by mode: `implement`/`light-implement` run `hooky run` (`--light` for the latter) as a subprocess; `review` runs `hooky review`; `refine` starts nothing.
- **What's different from workflow #1**: no GitHub-hosted runner, no git publishing. Triggered runs execute one at a time, serialized behind a lock, against the local workspace, and stop there — `hooky listen` never commits, pushes, or opens a PR/review. Role timeouts (`runtime/models.py`) use `SIGALRM`, which only works on a process's main thread; shelling out to a subprocess avoids that restriction and avoids mutating this process's environment from a background thread.
- **Why it's useful**: lets a user watch/debug a run with `hooky watch`/`hooky trace` in real time, iterate on the loop or prompts without pushing to GitHub, or use an executor (e.g. local `claude`/`codex`) that isn't available/authorized in CI.
- **Security**: `hooky listen --secret <shared-secret>` (or `HOOKY_WEBHOOK_SECRET`) verifies `X-Hub-Signature-256` before triggering anything; without it, any local process that can reach the bound port can start a run.
